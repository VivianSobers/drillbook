# v0.1 drill results

These are real runs of the five drills in [drills/](../drills) against the drill environment from `env/up.sh`. Every number on this page comes from `.drillbook/results.jsonl` and the drill logs of those runs. All times are UTC, on 2026-10-08.

The environment is two kubeadm nodes (`kindest/node:v1.36.4` with sshd) running as systemd containers on the local Docker daemon, with kube-prometheus-stack chart 92.1.1 pinned to the control plane and the shop demo service on the worker.

## Full run on the laptop

All five drills in one `drillbook run`, started 15:24:10 and finished 18:21:27, exit code 0. The binary reported version `976c018-dirty`: commit 976c018 plus uncommitted edits. `internal/engine` is the same at 976c018 and 17b6075. Two later commits change it: bb176c1 records why a control run got no result, and 3fb5d0a makes `abort` keep a silence while its alert fires. Neither case came up in these runs.

| Drill | Alert | Verdict | Fired after | Resolved after | Receiver | Control |
|---|---|---|---|---|---|---|
| shop-api-scaled-to-zero | ShopApiDown | pass | 1m45s | 31s | shop-team | held (cached) |
| shop-api-bad-image | KubeDeploymentRolloutStuck | pass | 17m31s | 30s | shop-team | held |
| shop-api-crashloop | KubePodCrashLooping | pass | 16m1s | 5m31s | shop-team | held (cached) |
| app-data-disk-full | NodeFilesystemAlmostOutOfSpace | pass | 30m46s | 33s | platform-oncall | held |
| kubelet-stopped | KubeNodeNotReady | pass | 16m30s | 38s | platform-oncall | held |

"Held" means the control run applied the same fault without the runbook and the alert was still firing at the end of `resolve_within`. Two controls came from the cache, keyed by the drill file's hash. They were recorded by real runs earlier the same day with the same drill files: scaled-to-zero at 13:50:40 and crashloop at 13:58:56.

Fire times are mostly the rules' own `for` durations: 1m for ShopApiDown, 15m for KubeDeploymentRolloutStuck, KubePodCrashLooping and KubeNodeNotReady, and 30m for NodeFilesystemAlmostOutOfSpace. Crashloop takes longer to resolve than the others because its expression is `max_over_time(...[5m])`, which keeps the alert up for about five minutes after the pod stops crashing. The drill's `expected_resolve` of 8m allows for that.

## Reproducing

```sh
env/up.sh
make build
bin/drillbook run shop-api-scaled-to-zero shop-api-bad-image shop-api-crashloop app-data-disk-full kubelet-stopped
bin/drillbook report
```

The laptop run took 2h57m with two controls cached, and the second-machine run took 3h34m with none. Most of that time is spent waiting out `for` durations.
